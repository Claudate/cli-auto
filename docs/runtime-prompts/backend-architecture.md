## 后端与工程架构（写计划 / 拆分时必须先定交付深度）

目标：先判断用户要的是**演示直出**还是**可运维可扩展工程**，再选语言、框架与分层；禁止一上来上 DDD/微服务，也禁止把演示站硬做成企业脚手架。

### 1. 交付深度（先选一档，写进计划「建议技术」）

| 档位 | 用户话术线索 | 交付物 | 架构默认 | 禁止 |
|------|--------------|--------|----------|------|
| **A · 演示直出** | 演示、路演、看看效果、原型、假数据就行、先做出来 | 可点的页面/脚本/单机小工具 | 无分层或「页面 + 假 API」；可 mock | 仓库脚手架、CI 全集、DDD、K8s |
| **B · 可用小产品** | 自己用、小团队用、能部署、有真数据 | 单体 API + 简单前端 + 一库 | **MVC 或 轻分层**（handler → service → repo） | 多仓微服务、完整领域事件 |
| **C · 可扩展工程** | 后期扩展、多人协作、运维、合规、长期维护 | 清晰边界 + 测试/配置/部署约定 | **按语言选主流骨架**（见下）；可谈模块边界 | 无验收的「先堆代码」 |
| **D · brownfield** | 改现有仓 / 加功能 | 挂载点 + 最小 diff | **冻结现有语言与架构** | 另起第二套框架/第二语言 |

**默认规则**

- 只说「做个网站/落地页/介绍页」→ **A**（静态/SSG；无后端或第三方表单）。
- 说「登录后办事 / 后台 / CRUD」但未提扩展 → **B**。
- 明确「框架完整、可运维、可扩展、团队」→ **C**；仍优先**单体**，微服务要有独立理由。
- 用户点名语言（Node/PHP/C#/Java/Go/Rust…）→ 尊重点名，只在档位内选该语言的**轻量主流**组合。
- 用户说「默认/你定」→ 按上表 + 下表默认，并在计划写「假设：交付深度 = X」。

**澄清（信息不足时 ≤2 题，勿盘问）**

1. 只要演示，还是要上线给真人用？  
2. 是否已定语言/必须对接现有系统？

### 2. 何时需要后端

| 需求 | 默认 | 说明 |
|------|------|------|
| 纯展示 / SEO 营销 | **无后端** | 静态或 SSG；配方 R-overseas/R-shanshui 等 |
| 留资表单 | 第三方表单 / 边缘函数 | A/B 档都可；R-waitlist |
| 登录、权限、持久业务数据、支付、文件、后台 | **需要后端** | B/C；R-tool / R-admin / 交易电商 |
| 仅桌面本地工具 | 本地进程即可 | 不必上 HTTP 服务 |

与前端站点类型咬合见 `ui-delivery-recipes.md` §4；**禁止** marketing 纯展示却搭 C 档微服务。

### 3. 语言与默认组合（绿野 · 按交付深度）

用户未指定语言时：Web API 偏 **Node** 或 **Go**；企业已有栈跟企业。**禁止**无依据同时引入 2 种后端语言。

| 语言 | A 演示 | B 可用小产品 | C 可扩展工程（仍单体优先） | 典型场景 |
|------|--------|--------------|----------------------------|----------|
| **Node** | Express/Fastify 单文件或 Next Route Handler + mock | Fastify/Nest **模块扁平** 或 Hono + Prisma/Drizzle + 一库 | Nest 模块化 **或** 自研 ports/adapters；非必要不上 monorepo 微服务 | 全栈 JS、出海 API、BFF |
| **PHP** | 单入口脚本 / 纯 HTML+PHP | Laravel 或 Symfony 轻用（MVC） | Laravel 领域模块 **或** Symfony 清晰 bundle；避免无必要微服务 | 内容站、中小后台、主机友好 |
| **C#** | 最小 Minimal API 单项目 | ASP.NET Core MVC/Minimal + EF Core | Clean Architecture / 垂直切片（按团队习惯）；**慎用**过重整仓模板 | Windows/Azure、企业内网 |
| **Java** | 单 class 主程序 / 极简 Spring 单模块 | Spring Boot **单模块** MVC | Spring Boot 多模块（api/app/domain/infra）或等价；**默认不对齐**完整 DDD 八股 | 企业、银行式约束 |
| **Go** | `net/http` 或 chi 单 main | chi/gin/echo + sqlc/ ent + 标准 layout | 标准 layout + interface 端口；可选 DDD 轻量；**禁止**无流量上 service mesh | CLI、高并发 API、运维友好 |
| **Rust** | 单 binary + axum 少路由 | axum/actix + sqlx + 模块目录 | 工作区多 crate（domain/app/infra）仅在 C 档且团队认 Rust | 性能/安全敏感、本仓类产品 |

**桌面/CLI 软件（非网站）**

- A：脚本或单目录可运行 demo。  
- B/C：跟平台（Tauri/Electron/.NET MAUI 等）或纯 CLI；UI 架构见下节，**不要**把 Web DDD 硬套进桌面壳。

### 4. 架构模式怎么选（给人话，不堆术语）

| 模式 | 一句话 | 适用 | 不适用 |
|------|--------|------|--------|
| **无架构 / 直出** | 页面或脚本直接出结果 | A 演示、静态站 | 多写者长期演进 |
| **MVC** | 请求 → 控制器 → 模型/视图 | B 档 Web、多数 CRUD | 复杂领域规则极多时需加应用层 |
| **MVVM** | 视图 ↔ 绑定 ↔ 视图模型 | 桌面/前端富交互（本产品桌面也走 MVVM） | 纯服务端 API 不必硬套 |
| **轻分层** | handler → application → 存储 | B→C 过渡 | A 演示 |
| **DDD / 六边形** | 领域模型与端口隔离基础设施 | **C 档**且业务规则复杂、多端入口 | A/B 默认；禁止「目录像 DDD、逻辑仍一团」 |
| **微服务** | 多独立部署单元 | 明确多团队/独立扩缩/合规隔离 | 演示、小产品、单人维护 |

**硬纪律**

1. **架构服务于交付深度**：A 不写 DDD；C 才谈限界上下文。  
2. **计划里写清**：交付深度 + 语言 + 框架 + 架构模式（无/MVC/轻分层/…）+ 一句话为什么。  
3. **brownfield**：只写挂载点与改哪些目录；不「升级成完整 DDD」。  
4. **扩展性**用可观察项表达：配置外置、单一数据入口、接口边界、基础日志/健康检查——不要只写「预留扩展」。  
5. **运维（C 档建议写入成功标准）**：一键或文档化启动、环境变量、健康检查、基础日志；A 档可省略。  
6. **禁止**：为简历式架构堆目录；A 档生成 `domain/application/infrastructure` 空壳。

### 5. 写进 ```plan / 拆分 body

**建议技术**（有后端或完整工程时尽量齐）：

```text
- 交付深度：A 演示 | B 小产品 | C 可扩展 | D 改现有
- 形态：静态 / SPA / 全栈 / API / CLI / 桌面
- 语言/框架：…
- 架构：无 | MVC | MVVM | 轻分层 | DDD/六边形（仅 C）
- 数据：无 | SQLite/Postgres/… | 第三方 BaaS
- 部署：…
- 为什么（一句话）：
```

**成功标准示例**

- A：主路径可点；演示数据注明；**无**强制企业脚手架。  
- B：注册/登录或核心 CRUD 真通；`README` 能本地起服务。  
- C：模块边界可指认；配置可切换环境；健康检查或等价探针；关键路径有测试或可勾选验收。

**拆分 do 步骤**

- body 写明交付深度；A 禁止拆「搭建完整 DDD 骨架」类任务。  
- C 的「搭骨架」一步须可验收（目录约定 + 一接口跑通），不要只建空文件夹。  
- scope_paths 按语言习惯（如 `src/`、`app/`、`cmd/`、`internal/`），禁止与前端抢同一巨石文件无说明。
