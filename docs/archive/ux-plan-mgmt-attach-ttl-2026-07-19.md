## 0. 一句话

**聊天默认全宽写计划；用户主动打开计划文件夹后才出现右栏「标题列表」；单击选中、双击编辑；保存问一次、分配点一次；能附图说明需求；聊天记录只留约 2 天。**

```text
【入口】无活动 run → 聊天主窗（全宽，右栏默认关）
【写】  多轮 + 可选附图 → CLI 草稿 →（自动/一点）CLI 规范化成模板 → 确认保存 .md
【管】  「计划管理」→ 打开/显示默认计划夹 → 右栏只显示标题 + 状态
【选】  单击 = 选中（高亮 + 就绪条绑定）；双击 = App 内编辑
【跑】  分配 → 方案 A chooser → Mode B（confirm_start 不变）
【净】  会话 JSON 超 2 天自动清理；顶栏最多 2～3 个主按钮
```

## 1. 截图与草稿问题诊断（2026-07-19）

### 1.1 截图：右侧「计划」像整篇正文

| 现象 | 根因（代码锚点） | 后果 |
|------|------------------|------|
| 右栏一行变成整篇 md 墙 | 落盘文件 `plans/chat-20260719-0902.md` **几乎无换行**（整文件一行）；`plan_title_hint` / `extract_title_from_md` / 前端 `planTitleFromMarkdown` 对 `# ` 后**整行**取标题 → 标题 = 全文 | 用户以为「计划管理坏了」 |
| 标题区无行数上限 | `.plan-rail-item-title` 仅 `word-break`，**无** `line-clamp` / `max-height` | 再长标题也会撑爆轨 |
| 路径次行仍占视线 | `.plan-rail-item-path` 默认全显 `plans/chat-….md` | 窄栏更挤；应用 `title` 悬停即可 |
| 右栏常显 | `#plan-rail` 进 chat 即占 240px | 与「默认不显示、打开文件夹才显」冲突 |

**标题提取正确行为（本计划冻结）：**

```text
1. 优先 front-matter / 显式 title 字段
2. 否则取首个 Markdown H1（# …），但：
   · 在遇到「##」「\n#」或行内「##」前截断
   · 最长 80 字；超出加「…」
3. 再否则用文件名 stem（chat-20260719-0902）
4. CSS：标题最多 2 行 + ellipsis；路径默认隐藏或单行 ellipsis
```

## 3. 设计原则（硬约束）

1. **上手简单**：新用户 3 步内写出并分配第一个计划  
   `选项目 → 聊天说需求（可附图）→ 保存 → 分配`  
2. **界面清晰**：默认只显示「当前该看的」；计划列表默认隐藏，不抢聊天  
3. **不杂乱**：顶栏最多 2～3 个主按钮；聊天区无多句常驻确认堆叠（对齐 P2-10）  
4. **流程短**：保存问一次、分配点一次；**不**平行第二套执行入口  

**不改：**

- Mode B `confirm_start` 契约  
- Scheduler 主语义（stall/failover 已在 H3/H4）  
- 方案 A（先 md 再分配 / chooser）

## 4. 修后主路径（唯一心智）

```text
① 侧栏选项目
② 无活动 run → 聊天主窗（全宽；右栏关）
③ 多轮澄清；可选 📎 附图
④ CLI 段 1「生成」：自由/大纲草稿（```plan 可有可糙）
⑤ CLI 段 2「规范化」（默认自动一次，可关 / 可「重新整理」）：
     · 输入 = 段 1 草稿 + 固定模板契约（见 §4.0）
     · 输出 = 结构完整、带换行、H1 短标题、可被 Mode B 拆分的 md
⑥ 用户点「保存为计划」→ 一次确认路径 → 写 .md（只写规范化后的正文）
⑦ 需要管计划时：顶栏「计划管理」
     · 首次：引导选择/确认默认计划文件夹（默认 <project>/plans）
     · 之后：打开右栏，列表 = 该目录下 .md 的【标题】+ 状态 badge
⑧ 单击某计划 → 选中（高亮；底条可「分配 / 预览」）
   双击 → 编辑 modal（未执行可覆盖；已执行另存副本）
⑨ 「分配计划」→ chooser（CLI/并发/暂停确认）→ Mode B
⑩ 有活动 run / 待回确认拆分 → 顶栏次要「返回执行/继续确认」（≠ 计划管理）
⑪ 会话：updated_at 刷新；>48h 的 chat JSON 清理
```

### 4.0 CLI 两段式：生成 → 规范化（采纳用户补充）

> **结论：比「单轮又聊又收格式」更好**，也比「只靠本地正则修标题」更能解决「计划太简单、和差异很大」。  
> 本地 G0 截断/换行仍保留作**防线**；内容质量靠段 2 CLI。

#### 4.0.1 为何更好

| 单轮现状 | 两段式 |
|----------|--------|
| 同一 prompt 既要澄清又要贴 fence，模型易糊成一段无换行墙 | 段 1 只管「说清楚要做什么」；段 2 只管「收成 cco 模板」 |
| 草稿过粗 → Mode B 拆出空/杂任务 | 模板强制目标/范围/任务/验收/非目标，拆分输入稳 |
| 右栏标题靠猜 H1 | 段 2 强制首行 `# 短标题`（≤40 字） |
| 用户感觉「计划和我想的差很远」 | 段 2 可对照用户原话补缺口；不满意可「重新整理」或回段 1 再聊 |

#### 4.0.2 与 Mode B 的边界（硬）

```text
段 1+2 聊天 CLI  →  散文 .md（计划文档）
Mode B Planner   →  任务图 / confirm_start
```

- 段 2 **禁止**输出 cco-plan/v1 JSON 或 TaskIR（仍归分配阶段）。  
- 段 2 **只**产出结构化 Markdown，让后续 Planner 更好拆，不替代 Planner。

#### 4.0.3 规范化模板契约（冻结 · 段 2 输出形状）

```markdown
# <短标题，≤40 字，单行>

## 目标
（1～3 句）

## 范围
- 做：…
- 不做：…

## 任务大纲
### T1 · <可执行标题>
- 说明：…
- 验收：…

### T2 · …
…

## 验收（整计划）
- [ ] …

## 风险与依赖
- …

## 说明
（可选：与已有能力边界一句）
```

硬规则（写入段 2 system/user 附加 prompt）：

1. **必须**多行 Markdown；禁止把全文挤成一行  
2. 首行必须是单一 `# 标题`，标题内禁止再出现 `##`  
3. 任务标题可执行、避免「分析一下」「优化体验」空壳；每任务带验收  
4. 不写「已完成」；不假装执行  
5. 若输入已是合格结构，只做轻量补全，不无故扩写  

#### 4.0.4 触发策略（默认）

| 时机 | 行为 |
|------|------|
| 段 1 抽出 `draft.markdown` 且用户未关「自动整理」 | **自动**跑段 2 一次，草稿卡片展示整理后版本 |
| 用户点「重新整理」 | 再跑段 2（可带用户一句附加约束） |
| 用户在卡片上直接编辑后保存 | 不再强制段 2；保存走规范化换行防线即可 |
| `CCO_CHAT_FAKE` / CLI 不可用 | 跳过段 2；本地模板或仅 G0 防线；UI 标明未整理 |
| 设置 | `chat_normalize_plan: true` 默认开；可关回单轮 |

#### 4.0.5 实现锚点（最小）

| 层 | 做法 |
|----|------|
| 服务 | `chat_normalize_plan(project, markdown, hint?)` → 调同一 Claude CLI，独立 prompt（模板契约 §4.0.3）；返回新 markdown + title |
| 会话 | `draft_plan` 可保留 `raw_markdown` + `markdown`（整理后）；UI 默认真 `markdown` |
| 发送路径 | `chat_send` 成功且有 fence → 可选链式 `normalize`（注意超时：段 2 timeout 可 120s） |
| 成本 | 多 1 次 CLI；可用「仅保存前整理」降频（备选：默认改为保存前一次，见 Q8） |

#### 4.0.6 与「差异很大」的关系

用户原话要的是**体验优化清单**（计划管理/附图/清理…），不是空的「全局分析」。段 2 模板逼模型：

- 把诉求拆成 **G0–G4 级可执行块**（或用户域任务）  
- 写出验收与非目标，避免和已落地 C0–C2/H0–H4 重复施工  
- 仍用**散文 md**，分配时 Mode B 再拆 worker 任务  

→ 从「一段口号」变成「可保存、可展示标题、可拆分」的计划。

### 4.1 顶栏（page=chat · 已选项目）

## 8. 风险与默认决策
