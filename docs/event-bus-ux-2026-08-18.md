## 0. 一句话

**事件总线不是工程炫技——它的用户价值只有一句话：把"等 2 秒才知道"变成"即时看到"。但如果做不好，会把"2 秒延迟"换成"状态闪烁/按钮跳变/降级突兀"，反而更差。本文把每条事件映射到一个具体的用户动作和一句人话文案，让 B1 落地时能在「技术上通了」之外回答「用户用起来顺不顺」。**

## 2. 每条事件的用户操作映射

> 每行：**事件 → 用户在做什么 → 看到什么 → 文案 → 时序要求**  
> 文案必须过规则 23（引擎名/VERDICT/schema/run_id 不进第一句）。

### 2.1 run 相事件（本期做）

| 事件 | 用户当下操作 | 看到什么变化 | 人话文案 | 时序要求 |
|------|-------------|-------------|---------|---------|
| `run_start` | 在拆分台点完「执行规划」→ 切到执行台 | 看板从空→出现第一批任务行（pending dot） | 不单独提示；看板出现即感知 | 切台前不要弹 toast（会被看板盖住） |
| `task_start` | 看着看板等任务跑 | 某任务卡：灰点→蓝点，标签「执行中」 | dot + 一行状态字，**不弹 toast** | **关键**：< 100ms 可接受；但要防抖（见 §3.1 闪烁） |
| `task_end`(done) | 等任务完成 | 卡片蓝点→绿点，标签「已完成」 | 不弹 toast；看板计数 +1 | < 100ms |
| `task_end`(failed) | 任务跑挂了 | 卡片蓝点→红点，标签「失败」+ 失败摘要 | **可弹一次 toast**：「任务 X 失败，查看详情」 | 失败要可见，不能被下一条事件盖掉（见 §3.2） |
| `checkpoint` | 任务失败后看是否有"从这里继续" | 日志栏「继续」按钮文案→「从这里继续」+ tooltip | "从最后一个完成步骤后继续执行" | 按钮文案在 100ms 内切换；切走再回来仍保持（run 还在） |
| `run_end` | 等整轮结束 | 自动切结果台 + 全量刷新 | 不弹 toast；切台即感知 | 切台与全量刷新必须原子（见 §3.3） |
| `permission_tier` | 高级用户在看安全标签 | 任务卡上出现小标签（ReadOnly/WorkspaceWrite/FullAccess） | **默认折叠**；只在设置开启"显示安全标签"时可见 | 非默认可见——规则 24 高级能力默认关 |

### 2.2 chat 相事件（后置 · 本期不做）

| 事件 | 用户当下操作 | 说明 |
|------|-------------|------|
| `context_compressed` | 在聊天台发消息 | 压缩感知可见——但走 `cco:chat_event` channel，**本期不通** |

## 3. 易用性关键点与缓解

### 3.1 U1 · 闪烁防抖（task_start/task_end 高频）

**问题**：并发任务多个 task_start 在 50ms 内连续到达，卡片在 50ms 内"灰→蓝→灰→蓝"跳变，用户会觉得卡顿。

**缓解**：
- **事件合并**：同一 task_id 的事件在 16ms（一帧）内合并，只渲染最终态；
- **状态过渡 CSS**：dot 颜色用 `transition: background 120ms`，视觉上"渐变"而非"闪"；
- **失败不合并**：task_end(failed) 必须立即渲染，不能被下一条 done 事件合并掉（见 §3.2）。

**验收**：看板在 3 个并发 task_start 同时到达时，用户感知不到多次跳变。

### 3.2 U2 · 失败可见性不被覆盖

**问题**：task_end(failed) 后 200ms 内另一个 task_end(done) 到达，增量 patch 会不会把失败态"覆盖"成 done？

**代码核对**（`RunView.js:332`、`loadLive.js` 的 `pickSelectedTaskId`）：
- 现状 `patchTask` 按 `task_id` 精确 patch，不会跨任务覆盖；
- 但 `run_end` 后的 `loadLive()` 全量刷新**会**按服务端 RunState 重写所有 task——如果 RunState 此时还没写完失败态，前端会"闪回 pending"。

**缓解**：
- `run_end` 后 `loadLive()` 延迟 300ms 再执行（等服务端 RunState 落盘）；
- 或：`run_end` 不立即 `loadLive()`，而是先 patch run 终态，等下一个 poll tick 自然刷新。

### 3.3 U3 · 降级体感

**问题**：事件通道断开（Tauri emit 失败/窗口失焦/IPC 抖动），用户看到"动了一下又卡住"。

**缓解**：
- `eventStale` 不只做单 tick 跳过，加**连续失败计数**：
  - 1-3 次失败：继续走事件通道（可能只是单次抖动）；
  - 连续 4 次失败：切回 2s 轮询，并在看板边缘显示"实时连接已降级"小条（**可关**，不阻塞）；
  - 事件恢复：立即切回事件通道，降级条消失。
- **不弹 modal / 不弹 toast**——降级是后台行为，用户不该被打断。

### 3.4 U4 · 安全标签默认折叠

**问题**：非开发用户看到"ReadOnly/WorkspaceWrite/FullAccess"会困惑。

**缓解**：
- 安全标签**默认不可见**（规则 24）；
- 设置页"高级"区加一个开关：「显示任务安全层级」；
- 开启后任务卡上出现小标签 + tooltip 人话解释；
- 人话文案：
  - ReadOnly → "只读（不写文件）"
  - WorkspaceWrite → "可写本项目"
  - FullAccess → "完全访问（谨慎）"
- **不**在主路径文案出现（规则 23）。

### 3.5 U5 · 多窗口一致性

**问题**：主窗 + 独立监视窗（`?cco_window=monitor`）都收到 emit，但两边渲染时序可能差 50-100ms，用户在两个屏幕看到"不同步"。

**缓解**：
- 监视窗是**只读观察**——不要求与主窗像素级同步；
- 但终态（run_end）两边必须一致：主窗切结果台时，监视窗也切到结果视图；
- 中间态差异可接受（本来就有网络/渲染差）。

### 3.6 U6 · 轮询退避

**问题**：`eventStale` 单 tick 跳过后，如果事件一直不来，每个 tick 都跳过=永远不轮询=前端永远卡在旧状态。

**缓解**（已在原计划 §3.3.2 部分提及，本文补全）：
- `eventStale` 每 tick 置 true，事件到达置 false；
- **连续 3 个 tick（6s）无事件** → 强制 `loadLive()` 一次（对账）；
- 对账后如果 RunState 也无变化 → 真的没在跑，正常。

## 4. 用户操作流（关键路径走查）

### 4.1 主路径：拆分 → 执行 → 失败 → 从断点继续

```
用户动作                    前端事件                          界面变化
─────────────────────────────────────────────────────────────────────
1. 拆分台点「执行规划」      confirm_start_cmd (gateway)      → 切执行台
2. (后端) run_start emit    → cco:run_event{type:run_start}   → 看板出现任务行
3. 等待…                    → task_start × N                   → 多卡变蓝（合并防抖）
4. 某任务完成               → task_end(done)                   → 卡变绿 + 计数+1
5. 某任务失败               → task_end(failed) + checkpoint    → 卡变红 + toast
                                                              + 「继续」→「从这里继续」
6. 用户点「从这里继续」      resume_run_cmd                    → 卡变蓝（重跑）
7. (后端) run_end emit      → cco:run_event{type:run_end}     → 切结果台 + 全量刷新
```

**关键时序**：
- 步骤 5 的 `task_end(failed)` 和 `checkpoint` 可能同一批到达——失败 toast 不能被 checkpoint 的按钮切换盖掉；
- 步骤 7 的 `run_end` 后 `loadLive()` 延迟 300ms（见 §3.2）。

### 4.2 降级路径：事件断开 → 轮询接替

```
用户动作                    前端状态                          界面变化
─────────────────────────────────────────────────────────────────────
1. 正常执行中               eventStale=false                  看板实时更新
2. (Tauri emit 抖动)         eventStale=true × 4               看板边缘出现"实时降级"小条
3. 退回 2s 轮询              loadLive() 每 2s                  看板 2s 跳一次（可接受）
4. 事件恢复                  eventStale=false                  小条消失，实时恢复
```

**关键**：步骤 2 的"降级小条"必须可关，且不阻塞操作（用户仍可点停止/继续）。

### 4.3 冷启动路径：打开 app → 看到活动 run

```
用户动作                    前端行为                          界面变化
─────────────────────────────────────────────────────────────────────
1. 打开 app                 boot() → loadProjects             → 项目列表
2. 有活动 run 的项目        H0 自动选中                       → 进执行台
3. (此时事件通道未订阅)     startPolling → loadLive           → 看板显示当前状态
4. 事件订阅就绪             subscribeRunEvents                → 后续实时更新
```

**关键**：步骤 3 到 4 之间，前端先用轮询拿到状态，事件订阅是"增量叠加"，不是"替换"。用户不会看到"先空→后有"。

## 5. 易上手校验清单（非开发视角）

> 给一个**完全不懂技术**的 PM 用，能否在 3 分钟内理解。

### 5.1 认知负担

| 检查项 | 通过标准 |
|--------|---------|
| 用户是否需要理解"事件总线"概念？ | **否**——这是实现细节，文档/UI 不出现这个词 |
| 用户是否需要理解"轮询降级"？ | **否**——降级小条文案："实时连接恢复中"，不提技术词 |
| 用户能否不看文档就知道"从这里继续"是什么？ | **是**——tooltip "从最后一个完成步骤后继续执行" |
| 安全标签是否会吓到非开发用户？ | **否**——默认不显示，开了也是人话 |

### 5.2 操作流顺畅度

| 检查项 | 通过标准 |
|--------|---------|
| 从拆分到看到任务跑起来，用户需要点几次？ | **1 次**（执行规划）+ 自动切台 |
| 任务失败后恢复需要几次点击？ | **1 次**（从这里继续） |
| 降级时用户能否继续操作？ | **是**——降级不阻塞，停止/继续按钮可用 |
| 切走再回来，状态是否保持？ | **是**——checkpoint 标记在 store 内，切台不丢 |

### 5.3 异常路径

| 检查项 | 通过标准 |
|--------|---------|
| 事件通道完全不可用（CLI 模式） | 退回纯轮询，行为与现状一致，无报错 |
| emit 高频风暴（100 条/秒） | 前端合并防抖，看板不卡顿 |
| RunState 与事件不一致 | run_end 后 300ms 延迟全量刷新对账 |
